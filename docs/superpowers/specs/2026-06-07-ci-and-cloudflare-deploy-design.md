# CI + Cloudflare deploy (beta.do.zone) — Design

**Date:** 2026-06-07
**Status:** Approved (design)
**Repo:** `reubenfirmin/thedozone2`

## Goal

1. Add CI that builds and tests `thedozone2` on every push and pull request.
2. Deploy the built static SPA to `beta.do.zone` on Cloudflare via Wrangler, automatically on every push to `main`.

Scope is **beta only**. A production `do.zone` environment is explicitly out of scope for now.

## Context / constraints discovered

- `thedozone2` is a Kotlin Multiplatform project with a single **JS (IR) browser** target. The app is a static SPA.
- The deployable site is assembled by the Gradle task **`jsBrowserDistribution`** into `build/dist/js/productionExecutable/`. This directory contains `main.bundle.js`, `index.html`, `style.css`, icons, and other processed resources. (`jsBrowserProductionWebpack` alone does **not** include the HTML/CSS/icon resources, so it is insufficient as a deploy artifact.)
- Tailwind CSS is generated by the Zoned plugin's **`build-style`** task, which writes `src/jsMain/resources/style.css` (consumed by `jsProcessResources`). It must run before the distribution is assembled.
- There are **22 `jsTest` test files** run via Karma + headless Chrome (`useChromeHeadless()`), so CI needs a Chrome binary available.
- **Critical dependency problem:** the build depends on private `1.0-SNAPSHOT` artifacts that only exist in the developer's local Maven cache (`~/.m2`):
  - Gradle plugin `io.4rc.zoned.plugin:1.0-SNAPSHOT`
  - `io.4rc:zoned-js:1.0-SNAPSHOT`
  - (transitively `io.4rc:zoned`, `io.4rc:zoned-jvm`, and a patched `kotlinx-html` fork resolved from JitPack)

  These are produced by the sibling repo `reubenfirmin/zoned` via `publishToMavenLocal`. There is **no remote registry** serving them. CI must therefore produce them itself.
- `zoned`'s own CI (`.github/workflows/ci.yml`) already demonstrates a working **bootstrap pattern**: because `zoned`'s root build applies its own plugin, it temporarily comments out the self-application (`sed`), publishes `:gradle-plugin` to Maven Local, restores the file, then runs the full build. We reuse this exact pattern.

## Decisions (from brainstorming)

| Question | Decision |
|---|---|
| Deploy mechanism | **Cloudflare Workers + Static Assets** (not Pages), driven entirely by Wrangler |
| `zoned` artifact strategy | **Build `zoned` in-CI** (checkout + bootstrap + `publishToMavenLocal`), no external registry |
| Deploy trigger | **Every push to `main`** + manual `workflow_dispatch` |
| Environments | **beta only** |

### Why Workers Static Assets over Pages

- Fully Wrangler-native; the entire config lives in a checked-in `wrangler.jsonc`.
- Cloudflare now steers new static projects to Workers static assets.
- Built-in SPA fallback via `assets.not_found_handling = "single-page-application"`.
- `beta.do.zone` attaches as a Worker **custom domain**, and Wrangler creates the required DNS record automatically (given the zone is on Cloudflare).

## Architecture

Data flow:

```
reubenfirmin/zoned  --publishToMavenLocal-->  ~/.m2 (io.4rc:*:1.0-SNAPSHOT)
        |
        v
thedozone2 build  --build-style + jsBrowserDistribution-->  build/dist/js/productionExecutable/
        |
        v
GitHub Actions artifact  --(deploy job)-->  npx wrangler deploy  -->  beta.do.zone (Cloudflare Worker + static assets)
```

### Files added

1. **`wrangler.jsonc`** (repo root)
   - `name`: `thedozone2-beta`
   - `compatibility_date`: current date
   - `assets`:
     - `directory`: `build/dist/js/productionExecutable`
     - `not_found_handling`: `single-page-application`
   - Custom domain `beta.do.zone` (configured as a Worker custom domain; see prerequisites).
   - No Worker script entry point is required for a pure static-assets Worker.

2. **`.github/workflows/ci.yml`** — two jobs (see below).

### CI workflow (`ci.yml`)

Triggers:
- `push` (all branches) and `pull_request` → run the `build` job.
- `push` to `main` and `workflow_dispatch` → additionally run the `deploy` job.

Concurrency: group per ref, cancel in-progress (same as `zoned`).

**Job `build`** (always runs):
1. `actions/checkout` for `thedozone2`.
2. `actions/checkout` for `reubenfirmin/zoned` at ref `master` into a sibling path (e.g. `../zoned`). Ref is a workflow-level constant so it is easy to pin to a commit later.
3. `actions/setup-java` (temurin, JDK 21).
4. `gradle/actions/setup-gradle` (Gradle caching).
5. Provide headless Chrome for Karma (e.g. `browser-actions/setup-chrome`, exporting `CHROME_BIN`).
6. Bootstrap + publish `zoned` to Maven Local:
   ```bash
   cd ../zoned
   chmod +x ./gradlew
   sed -i 's#id("io.4rc.zoned.plugin")#// id("io.4rc.zoned.plugin")#' build.gradle.kts
   ./gradlew --no-daemon :gradle-plugin:publishToMavenLocal
   git checkout -- build.gradle.kts
   ./gradlew --no-daemon publishToMavenLocal
   ```
   This places **all** `io.4rc:*:1.0-SNAPSHOT` artifacts in `~/.m2`.
7. Build + test `thedozone2`:
   ```bash
   ./gradlew --no-daemon build-style build jsBrowserDistribution
   ```
   (`build` runs the 22 Karma tests; `build-style` generates the Tailwind CSS; `jsBrowserDistribution` assembles the deployable site.)
8. `actions/upload-artifact`:
   - `site` ← `build/dist/js/productionExecutable`
   - `test-results` ← `build/test-results/**`, `build/reports/tests/**` (`if: always()`)

**Job `deploy`** (`needs: build`; `if: github.ref == 'refs/heads/main'` OR `workflow_dispatch`):
1. `actions/download-artifact` (`site` → `build/dist/js/productionExecutable`).
2. `actions/setup-node`.
3. `npx wrangler deploy`.
4. Auth via env:
   - `CLOUDFLARE_API_TOKEN` ← repo secret
   - `CLOUDFLARE_ACCOUNT_ID` ← repo secret

Building `zoned` once and passing the dist between jobs (via artifact) avoids a double build and keeps the deploy job lean (no JDK/Gradle).

## Manual prerequisites (one-time, owner-performed)

These cannot be done from this repo and require the owner's Cloudflare credentials:

1. **`do.zone` must be an active zone in the target Cloudflare account.** This is required so that `beta.do.zone` DNS can be created for the Worker custom domain.
2. **Create a Cloudflare API token** with the scopes needed for `wrangler deploy` of a Worker with static assets + custom domain. At minimum:
   - Account → *Workers Scripts*: Edit
   - Zone (`do.zone`) → *Workers Routes*: Edit
   - Zone (`do.zone`) → *DNS*: Edit (for the custom-domain record)
   - Account → *Account Settings*: Read (account resolution)
   (Exact scope list to be confirmed against current Cloudflare docs during implementation.)
3. **Add repo secrets** `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`.
4. The **first deploy is owner-triggered/verified**, since CI credentials are owner-supplied.

## Error handling / edge cases

- **`zoned` build fails** → `build` job fails fast; nothing is deployed. Surfaced via the bootstrap/publish step.
- **Tests fail** → `build` fails; `deploy` (which `needs: build`) is skipped. Test results still uploaded (`if: always()`).
- **Chrome missing** → Karma tests fail; addressed by the setup-chrome step.
- **Missing Cloudflare secrets** → `deploy` fails at the wrangler step with a clear auth error; `build` is unaffected, so PRs/branches still get green CI.
- **`zoned` master drift breaking the build** → mitigated by keeping the `zoned` ref as a single workflow constant that can be pinned to a known-good commit.

## Out of scope

- Production `do.zone` environment / promotion flow.
- Per-branch preview deployments.
- Publishing `zoned` artifacts to a remote registry (revisit if in-CI builds become too slow).
- Caching the published `zoned` artifacts across runs (possible later optimization).
